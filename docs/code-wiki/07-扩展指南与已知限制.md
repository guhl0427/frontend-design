# 07 · 扩展指南与已知限制

> 本项目的「扩展」几乎全部落在三处：数据、变体枚举、导出格式。每处都有必须同步的清单，漏一处不会报错，但会在运行时静默失效。

---

## 1. 新增一条风格

### 1.1 前置检查（最容易跳过、后果最大）

1. **查同分类既有条目的 `palette` 与 `headingFont`**，不能只看 `id`。
   曾经有一版初稿的「新中式」与既有 `guochao`（nameZh 已是「新中式国风」）直接撞车，只能整条换掉。
2. 确认差异点至少落在两处：主色相（`bg` / `accent`）、标题字体族、组件变体（`buttonVariant` / `cardVariant`）。
3. 若差异只体现在「文案口吻」，不要新增条目 —— 用定制抽屉的品牌占位符即可。

### 1.2 操作步骤

| 步 | 动作 | 位置 |
| --- | --- | --- |
| 1 | 追加 `StyleItem` 对象到数组末尾 | `src/data/styles.ts` 的 `STYLES` |
| 2 | `id`：kebab-case、全局唯一、**语义化且不再改**（进 URL / 收藏 / 文件名） | 同上 |
| 3 | `preview` 补齐 11 个必填键；色值统一用 `hsl(H S% L%)` 空格语法 | 同上 |
| 4 | 写 `prompt`：7 段、300–900 字符、每段含具体数值、禁用空话与占位符 | 同上 |
| 5 | 若用了**新字体**：先在 `index.html` 的 Google Fonts `<link>` 加 `family=`，可选再加入 `FONT_OPTIONS` | `index.html` / `src/data/fonts.ts` |
| 6 | `node scripts/verify-styles.mjs` | 终端 |
| 7 | 改 `TOTAL_STYLES` 为 36 | `scripts/verify-ui.cjs` |
| 8 | `npm run build` + 起服务跑 `verify:ui` | 终端 |

### 1.3 一条合格的风格数据长什么样

```ts
{
  id: 'dark-academia',                 // 稳定标识
  nameZh: '学院暗调',
  nameEn: 'Dark Academia',
  category: '复古',
  tags: ['深棕', '羊皮纸', '衬线', '书斋'],
  summary: '深胡桃木与羊皮纸的深夜书斋：酒红书脊、黄铜细线与索引式编排。',
  preview: {
    palette: {
      bg: 'hsl(28 18% 12%)', surface: 'hsl(30 20% 18%)',
      text: 'hsl(42 30% 90%)', textMuted: 'hsl(40 12% 72%)',
      accent: 'hsl(355 45% 38%)', accentText: 'hsl(40 35% 94%)',
      border: 'hsl(35 18% 30%)', shadowColor: 'hsl(28 25% 6% / 0.50)',
    },
    headingFont: '"Playfair Display", serif',
    bodyFont: '"Noto Serif SC", serif',
    radius: '2px', borderWidth: '1px',
    shadow: '0 8px 22px hsl(28 25% 6% / 0.45)',
    titleWeight: 600, titleLetterSpacing: '0.02em', uppercaseTitle: false,
    buttonVariant: 'solid', cardVariant: 'outline',
    backgroundImage: 'radial-gradient(circle at 50% -12%, hsl(38 35% 30% / 0.85), transparent 62%)',
  },
  prompt: `# 角色定位
…`,
}
```

### 1.4 校验会替你抓到什么

| 你可能会犯的错 | 谁抓到 |
| --- | --- |
| 忘写 `backgroundImage` 之外的必填键 | `verify:data` §1（`undefined` 或空串即 error） |
| 字体名拼错、或没在 `index.html` 引入 | `verify:data` §2 |
| `textMuted` 调得太浅 | `verify:data` §3（warn，但这是项目底线，应视为 error 处理） |
| 漏了一段（如「间距与圆角」） | `verify:data` §1（按字面量标题匹配） |
| 用了 `buttonVariant: 'neumorph'` 这类不存在的名字 | TS 类型 + `verify:data` §1 双重拦截 |
| 忘了改 `TOTAL_STYLES` | `verify:ui` 的 `F2b` / `F9c` |
| 预览在深色底上看不清（`inset` / `sketch` 的硬编码浅色阴影） | **无人抓到**，必须人工看样张 |

## 2. 新增预览变体

### 2.1 按钮变体（`ButtonVariant`）

| 步 | 动作 | 位置 |
| --- | --- | --- |
| 1 | 加字面量 | `src/types.ts` |
| 2 | 加字符串 | `scripts/verify-styles.mjs` 的 `BUTTON_VARIANTS` |
| 3 | 加 `case` 分支 | `src/components/Preview.tsx` 的 `primaryButtonStyle` |
| 4 | 若该变体需要改文案（如 `terminal` 的 `$ ` 前缀），同步 | `Preview` 的按钮渲染处 |
| 5 | 决定次级按钮是否特殊处理 | `secondaryButtonStyle` |

### 2.2 卡片变体（`CardVariant`）

同上，改 `CARD_VARIANTS` 与 `miniCardStyle`。

**新增变体时的两个判断**：

- 是否读 `cfg.shadow` / `cfg.radius`？读则跟随风格，不读则成为「质感例外」（现有例外：`inset`、`sketch`、`glass`、`acrylic`、`liquid`、`clay`、`riso` 的部分属性）。
- 在 216px 高、三张并排、每张约 90px 宽的尺寸下是否还看得见？`sketch` 的旋转之所以是 `-0.6deg` 而非 `-3deg`，就是这个约束的结果。

## 3. 新增分类

分类是**四处联动**，缺任一处都会造成「条目存在但筛不到 / 链接打不开」。

| 步 | 文件 | 改动 |
| --- | --- | --- |
| 1 | `src/types.ts` | `StyleCategory` 加字面量 |
| 2 | `src/data/styles.ts` | `CATEGORIES` 加中文名（**数组顺序即 tab 顺序**） |
| 3 | `src/utils/viewState.ts` | `CATEGORY_SLUGS` 加「中文名 → 英文 slug」 |
| 4 | 数据条目 | 至少一条使用该分类 |

新增后自检：

- `verify:data` 的 `分类分布` 应出现新键，且计数 > 0；
- 手动点该分类 tab，URL 应变为 `?cat=<slug>`；
- 若该分类只有 1–3 条，滚动到底部验证 sticky 筛选栏仍钉顶（`REG1` 覆盖的就是这类稀疏分类）。

**空分类不报错**：若加了 `CATEGORIES` 却没有条目，会渲染出一个永远 0 条的 tab，点击后显示「没有匹配的风格…」。视觉上不算 bug，但属于内容缺口。

## 4. 新增导出格式

以「导出 Tailwind 主题配置」为例：

| 步 | 动作 |
| --- | --- |
| 1 | 在 `src/utils/export.ts` 加 `buildXxx(item)` 与 `xxxFilename(item)` |
| 2 | 需要按段取内容时复用 `splitPrompt`，**不要再写一套正则** |
| 3 | 入口加在 `PromptDetail` 的动作行（注意已有 8 个动作，再加会拥挤，优先考虑收进菜单）或 `App` 的工具行 |
| 4 | 在 `scripts/verify-ui.cjs` 加断言：拦 `URL.createObjectURL` 读 Blob 文本，校验文件名与关键字段 |
| 5 | 在本文档 02 §2.4 / 04 §7.4 补充说明 |

**注意两个既有约定**：

- 合集导出必然包含「导出时间 + 数量 + 目录」，然后是逐篇正文；分篇之间用 `\n\n---\n\n` 分隔。
- 正文中的标题要降一级（`#` → `##`），否则与文档自身大纲冲突（`buildBundleMarkdown` 已处理）。

## 5. 新增定制参数

| 步 | 文件 | 改动 |
| --- | --- | --- |
| 1 | `src/types.ts` | `CustomizeTuning` 加字段（1–10） |
| 2 | `src/utils/promptComposer.ts` | `DEFAULT_CUSTOMIZE` 给默认值；加 `describeXxx` 四段阶梯；加入 `composePrompt` 的 `tuningLines` |
| 3 | 同上 | 若该参数影响预览，在 `derivePreview` 里映射为具体样式 |
| 4 | `src/components/Customizer.tsx` | `TUNING_META` 加一项（顺序即 UI 顺序） |
| 5 | `scripts/verify-ui.cjs` | 若断言依赖滑块索引，需同步；`F4b` 目前按 `#tuning-density` / `#tuning-variance` 的 id 定位，较稳 |

**原则**：参数必须能落到「具体数值 + 具体文案」，不能是「更现代一些」这类形容词。现有三档的文案均带 px / ms / 比例，是可直接抄的模板。

## 6. 已知限制（按影响排序）

| # | 限制 | 影响 | 现状 / 规避 |
| --- | --- | --- | --- |
| 1 | **隐私模式下收藏静默失效** | 用户以为已收藏，刷新即丢，且没有任何提示 | `useLibrary.writeIds` catch 后静默；`useCopy` 复制失败同样不置 `copied`。**建议后续加一次可见提示** |
| 2 | **预览是 `<button>` 内嵌块级元素** | `<div>` / `<h4>` / `<p>` 位于 button 内，不符合 HTML 内容模型（button 只允许 phrasing content） | 浏览器容错，功能正常；`W3` 断言依赖该结构，改结构需同步改测试 |
| 3 | **无错误边界** | 任一组件渲染抛错 → 整页白屏 | 无 `ErrorBoundary`；数据由 `verify:data` 把关，风险主要来自手工改代码 |
| 4 | **无 CI** | 验证依赖本地脚本；`verify:ui` 还依赖仓库外的 `playwright-core` 与本机 Chromium | 提交前手动 `npm run verify`；发版前手动跑 UI 断言 |
| 5 | **对比视图「缺段显示 —」永不命中** | 该分支在当前 35 条完整数据下不可达，等于未验证 | 若将来允许精简提示词，需要先补测试 |
| 6 | **跨标签页 `storage` 同步未自动化** | 多标签场景可能回归而不自知 | 逻辑简单，靠人工双开验证 |
| 7 | **定制参数不持久化** | 关闭抽屉即丢失，重开回到默认 5/5/5 | 有意取舍：定制结果是「一次性生成物」，不是配置 |
| 8 | **单条 DESIGN.md 文件名恒为 `DESIGN.md`** | 连续下载多条会同名，浏览器自动加 `(1)` | 设计上是为了能直接落到项目根目录；需要区分时用合集导出 |
| 9 | **`motion` 参数不影响预览** | 用户调「动效强度」时预览毫无变化，可能误以为失效 | 抽屉内有说明文案（「动效强度只写入提示词文本」） |
| 10 | **搜索不支持拼音与分词** | 输入 `baohao` 或 `包 豪 斯` 搜不到「包豪斯」 | 只做子串匹配；条目少时可接受 |
| 11 | **无 SSR / 首屏依赖 JS** | 首屏白屏时间取决于 JS 解析；不利于 SEO | 静态内容型产品，且 JS 108 kB gzip 可接受 |
| 12 | **`og:image` 缺失** | 社交分享无封面图，只有文本卡片 | 需部署后补 1200×630 PNG 与线上绝对 `og:url` |
| 13 | **变体内的硬编码色值** | `inset` / `sketch` 的浮雕色、`glass` 的白色叠加、`liquid` 的蓝色投影在部分色板上不成立 | 属刻意质感；换风格时必须人工看样张 |
| 14 | **字体清单双维护** | `index.html` 的 27 个 `family=` 与 `FONT_OPTIONS` 手工同步 | `verify:data` 只校验「数据引用的字体已引入」，不校验「`FONT_OPTIONS` ⊆ 已引入」 |
| 15 | **单文件数据 2191 行** | 多人并行改内容时合并冲突概率高 | 无拆分计划（拆分会带来 import 顺序与类型分散问题） |

### 6.1 刻意的不均衡

| 现象 | 说明 |
| --- | --- |
| 国风仅 1 条、极简 3 条 | 为避免同分类内调色板与标题字体重复而刻意留白。补条目前需先确认差异点（候选方向：敦煌矿物色、宋代文人青绿） |
| `corporate-memphis` 预览看不出「扁平插画」 | `Preview` 没有插画槽位，只能用色板与字体区分。属组件能力的边界，不是数据问题 |
| 复古 8 条、现代 6 条偏多 | 这两个方向的视觉差异最容易做出来，也最常被使用 |

## 7. 明确不建议做的（防过度工程）

以下都是「看起来合理、实际会破坏现有优势」的方向，评审时应主动否决：

| 提议 | 为什么不做 |
| --- | --- |
| 引入路由库 / 改成多页 | 单页 + 三个查询参数已覆盖全部需求；多页会让「同屏对比」这类交互成本上升 |
| 引入状态库（zustand/redux） | 状态总量 7 个 `useState`，且全部集中在 App；引入后只增加间接层 |
| 引入 UI 组件库 | 外壳视觉是定制方向，组件库的默认值几乎都要覆盖，净收益为负 |
| 引入 Markdown 渲染库（marked/react-markdown） | 只需 `#` `##` `- ` 三种语法，自研 60 行；引入后还要处理 XSS 与样式覆盖 |
| 引入测试框架（vitest/playwright test） | 现有两个脚本已覆盖数据与真实 DOM；换框架会带来配置、并行隔离、CI 依赖等一串问题 |
| 把数据拆成 35 个文件或迁到 JSON/CMS | 会失去类型约束与同文件可 diff 的优势；当前规模（35 条）不需要 |
| 给预览加动画/视频 | 预览的作用是「静态凭证」；动效会掩盖风格缺陷，也会让 35 张卡片同时动起来 |
| 为预览引入真实组件渲染（iframe/沙箱） | 体积与复杂度激增，且无法在 216px 尺寸内稳定呈现 |
| 用 CSS 变量替代内联样式做预览 | 35 套变量需要 35 个作用域类，动态性反而不如内联对象；且无法按变体分派复杂阴影 |

## 8. 技术债清单

按「修起来划算」排序：

1. **收藏 / 复制的失败反馈**（限制 #1）—— 一个 toast 的成本，直接消除「以为成功了」的困惑。
2. **`TOTAL_STYLES` 自动化** —— 让 `verify-ui.cjs` 从 `verify:data` 的产物或 esbuild 读数据，删掉手写常量。这是当前最容易漏改的一处。
3. **预览结构的 HTML 合规**（限制 #2）—— 把预览内容改为 `span` + `display:block` 或 `div` 外层结构调整，同时改 `W3` 断言。
4. **`playwright-core` 显式声明或提供安装脚本** —— 目前靠托管工作区路径，换机器即断。
5. **`FONT_OPTIONS` 与 `index.html` 的一致性校验** —— 补一条断言即可，成本极低。
6. **错误边界** —— 一个 20 行的 `ErrorBoundary` 可把「白屏」变成「可恢复的错误页」。
7. **`inset` / `sketch` 的硬编码色值参数化** —— 收益中等（会改变现有观感），需先确认视觉方向。
